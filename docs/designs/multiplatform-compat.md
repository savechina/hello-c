## Problem Statement

教程仓库声称支持 macOS、Linux、Solaris（=illumos 系，含 OmniOS）、FreeBSD，但样例代码只在 macOS（Apple clang）上被日常构建验证。2026-10-24 用户在 FreeBSD 上用 gmake 构建报错：`wide_locale_sample.c:109` 的 `%lc` 形参是 `wint_t`（FreeBSD 上为 `int`）而实参 `wchar_t` 是 `unsigned int`，触发 `-Werror -Wformat`。同样的平台特异回归可能还潜伏在其他约 100 个样例文件里（FreeBSD `wchar_t`=unsigned int、illumos `__sun` 分支完整性、socket/EPOLL/mmap 等 API 分叉）。

## What Makes This Cool

事故本身可以变成教材资产：把「三层移植策略（ISO C 优先 → 特性探测 → 平台 ifdef 兜底）」写成独立教学章节，用 wide_locale 的真实事故做开篇错例——这正是该教程 error-first 定位的最有力案例。同时 CI 矩阵闭环让"平台矩阵"这一个卖点从 README 声明变成可验证事实。

## Constraints

- 本地是 macOS（Apple clang 无 -fanalyzer；无 arm64 Valgrind；LSan 检测在 Darwin 默认关闭），FreeBSD/illumos 行为无法本地验证，只能靠 CI VM job
- CI 已有 build/test/asan/tsan 门禁（2026-10-23 加入），新增平台工作须融入现有 `.github/workflows/test.yml` 而不是另起工作流
- Dockerfile 有 mingw 交叉工具链，可用作交叉编译冒烟（不能替代原生验证）
- 教学约定：双语注释、每章 `main_<topic>_sample()` 入口、有界字符串操作

## Premises

1. 本地 macOS 无法验证 FreeBSD/illumos 差异——兼容性验收必须靠 CI matrix（freebsd 用 vmactions/freebsd-vm 或 cross-platform-actions；omnios 有 vmactions/omnios-vm）——用户同意
2. 教程样例优先 ISO C；仅 sysinfo/web/socket 等系统层章节允许平台分叉 —— 用户同意
3. 当前 CI 只有 macOS/Linux，没有 BSD/illumos 阵列，平台特异回归会静默进场——用户同意

## Approaches Considered

### Approach A: 最小修复 + 单 FreeBSD CI
Effort M / Risk Low（human ~1天 / CC ~30min）。只修实测 bug，CI 加一个 freebsd-vm job。OmniOS 验收不闭环，记 TODOS。

### Approach B: 全平台矩阵 + 兼容策略落地（选定）
Effort L / Risk Med（human ~3-5天 / CC ~2-4h）。CI 加 freebsd + omnios 两个 VM job；修全部 P1/P2；sysinfo illumos 分支核对补全；「三层移植策略」新章节（含本次事故案例）；修复共享化为 helper（bounded snprintf 追加、宽字符往返预留 MB_CUR_MAX）。

### Approach C: Docker 交叉编译矩阵替代 VM（已否决）
Effort S / Risk Low。复用 Dockerfile 矩阵交叉编译。否决理由：交叉编译 ≠ 原生运行，无法捕捉 libc 运行时行为差异——而 wide_locale bug 恰好属于此类，验收标准会落空。可作 Approach B 的补充门禁而非替代。

## Recommended Approach

Approach B（用户选择）。理由映射到验收：只有 B 同时满足「全平台可用 + CI 佐证」，且把事故转化为教材资产。
